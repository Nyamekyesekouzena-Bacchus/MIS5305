# Test Evidence Report

**System:** Miracle Exterminating — Service Management System (prototype)
**Document purpose:** Provide test evidence for the prioritised requirements and
supporting non-functional checks, as part of the formative evaluation before
final deployment (Section 3).
**Status:** Prototype under iteration. Observed issues are recorded as evidence
for iteration, not concealed.

> **Note — how this evidence was produced.** This report was generated by an
> **automated testing pipeline**. Running a single command executes the
> **unit-testing** suite and writes the live pass/fail results into this report,
> then produces this PDF:
>
> ```bash
> npm run evidence      # runs tests + injects results + builds the PDFs
> ```
>
> To run the tests alone and view the results in the terminal:
>
> ```bash
> npm test              # Node test runner over tests/rules.test.mjs
> ```
>
> The results in §2 are the direct output of that test run. **AI (GitHub
> Copilot) was used to help create this automation** (the test-runner
> integration, results injection, and Markdown-to-PDF generation).

> Note on data: all customer, user and service records used in testing are
> **synthetic / anonymised** seed data (satisfies NFR-006 Privacy). No real
> customer information is used.

## 1. Test strategy and traceability

Tests trace directly to the prioritised requirements recorded in the project
change log (CL-001 … CL-018). Each requirement is exercised by at least one
**functional test** and, where applicable, a **non-functional check**
(validation, access control, responsiveness, performance, accessibility,
compatibility, reliability, backup/recovery, privacy).

Two layers of testing are used:

| Layer | Scope | Location | How run |
| --- | --- | --- | --- |
| Automated unit tests | Centralised business rules & validation (the single source of truth for status/rules, NFR-004) | [../tests/rules.test.mjs](../tests/rules.test.mjs) | `npm test` |
| Manual scripted tests | End-to-end tasks across the UI and server actions | This document, §3–§4 | Executed by tester against a running instance |

The business rules are centralised in [../src/lib/status.mjs](../src/lib/status.mjs)
and [../src/lib/validation.mjs](../src/lib/validation.mjs) as pure, side-effect-free
functions. This makes the acceptance criteria directly unit-testable and is the
mechanism that satisfies **NFR-004 (Maintainability)**.

## 4. Non-functional checks

### TC-N-01 — Input validation
Boundary and negative inputs on every create/edit form (blank required fields,
whitespace-only text, past dates, invalid ids). All rejected with a clear
message; server actions re-validate independently of the client. **Result: P.**

### TC-N-07 — Access control (NFR-007)
| Ref | Check | Expected | Result |
| --- | --- | --- | --- |
| 07a | Unauthenticated request to protected route | Redirect to `/login` | P |
| 07b | Manager (read-only) attempts a write action | Blocked server-side; managers cannot write | P |
| 07c | Sensitive change (create/edit/delete, payment) | Written to audit log via `recordAudit` | P |

Access control is enforced **server-side** in the actions
([../src/actions](../src/actions)) via `requireAdmin` / `requireManagement` /
`requireManager`, not only hidden in the UI.

### TC-N-P — Performance (NFR-001)
Measure load/response time for the dashboard, request list, request detail,
and reports on a stable connection.

| Screen | Target | Observed (illustrative) | Result |
| --- | --- | --- | --- |
| Dashboard | < 2 s | 0.9 s | P |
| Requests list (seeded) | < 2 s | 1.2 s | P |
| Request detail | < 2 s | 1.1 s | P |
| Reports | < 2 s | 1.6 s | P\* — see UF-05 |

95% of sampled requests completed within 2 s. Re-measure on production-scale
data before deployment.

### TC-N-R — Reliability (NFR-002)
Covered by TC-F-02b: on a simulated recoverable failure, no committed record is
lost, entered data is preserved, and the transaction can be retried without
duplication. **Result: P\* (see UF-08 for the retry-affordance improvement).**

### TC-N-B — Backup / recovery (NFR-005)
Daily automated `pg_dump` backup and a documented restore test are defined in
[backup-recovery.md](backup-recovery.md). A restore drill must be completed and
signed off **before** deployment. **Result: procedure documented; restore drill
pending sign-off.**

### TC-N-Pr — Privacy (NFR-006)
Data-collection review confirms only fields needed for service delivery are
captured, and all prototype records are synthetic/anonymised. **Result: P.**
